# UX-001 — QBO-to-BBB Workflow and Screen Specification

Status: implementation contract for P-009

Scope: student application only
Case baseline: Suncoast Home Services LLC, June 2026

## 1. Product rule

BBB does not visually clone QuickBooks Online. It intentionally mirrors the bookkeeping workflow and vocabulary a QBO-certified student should recognize, then adds investigation, evidence, client communication, coaching, consequences, close review, and readiness reporting.

The complete learning loop is:

> See → Investigate → Verify → Communicate → Decide → Record → Reconcile → Explain

The interface must never turn the engagement into a visible answer hunt. Before final assessment, no screen may show scenario IDs, problem counts, task counts derived from hidden controls, correctness indicators, points, percentages, predicted readiness, or clean-master comparisons. Financial differences and operational status are allowed only when they arise naturally from the student's own books or an independent source such as a statement.

P-009 must compose the existing P-000–P-008 domain behavior. It must not implement substitute accounting, evidence, interaction, coaching, assessment, or report logic in UI components.

### 1.1 End-to-end student journey

The application supports this non-linear professional journey:

```text
Start Lab → Meet Suncoast → review business context
          ↓
Dashboard ↔ Bank Transactions ↔ Sales / Customers
          ↔ Expenses / Credit Card ↔ Chart of Accounts / Registers
          ↔ Documents ↔ Client Inbox ↔ BBB Coach
          ↔ Reports ↔ Reconcile Checking / Visa
          ↓
Close Books → Final Client Meeting → Client Readiness Report
```

`Start Lab` creates or resumes the student's authorized Suncoast attempt. `Meet Suncoast` is a short, student-safe engagement overview containing the company, bookkeeping period, client contact, scope of work, and navigation into the books. It contains no list of planted issues, required solution path, expected balances, hidden evidence inventory, or assessment mechanics.

The middle of the journey is intentionally non-linear. No scenario router advances the student from one hidden control to the next. The student may move among ordinary bookkeeping, reports, documents, Michael, and private coaching in the order their investigation requires. Only Close Books, Final Client Meeting, and Results have explicit server-owned gates.

## 2. Fidelity model

The normative fidelity values are `LOW`, `MODERATE`, `HIGH`, `VERY_HIGH`, `BBB_EXTENDED`, and `BBB_SPECIFIC`.

| Real bookkeeping surface | BBB surface | Fidelity | Intentional BBB difference |
| --- | --- | --- | --- |
| QBO Dashboard | Dashboard | `MODERATE` | Engagement orientation and workflow entry, not QBO visual imitation |
| Bank Transactions | Bank Transactions | `HIGH` | Evidence and client-contact paths sit beside bookkeeping decisions |
| Sales / Customers | Sales & Customers | `HIGH` | Full customer → invoice → payment → deposit trace |
| Invoices | Invoices | `HIGH` | Attempt-owned operational records only |
| Receive Payment | Receive Payment / Payment History | `HIGH` | Payment applications and Undeposited Funds remain explicit |
| Bank Deposit | Bank Deposits | `HIGH` | Deposit membership and source payments are inspectable |
| Expenses | Expenses | `HIGH` | Drill-through to journal and source evidence where authorized |
| Credit Card | Credit Card Transactions / Register | `HIGH` | Charge, liability, payment, and independent statement relationship |
| Chart of Accounts | Chart of Accounts | `HIGH` | Account type, balance, register, and consolidation context |
| Account Register | Registers | `HIGH` | Running balance from journal lines |
| Reconcile | Reconcile | `VERY_HIGH` | Beginning balance, ending balance/date, cleared rows, natural difference |
| P&L / Balance Sheet / A/R | Reports | `VERY_HIGH` | Ledger-derived output with transaction drill-through |
| Attachments | Documents | `BBB_EXTENDED` | Availability/unlock state, document requests, and audit-preserving access |
| N/A | Client Inbox | `BBB_SPECIFIC` | Exact student/client chronology and evidence requests |
| N/A | BBB Coach | `BBB_SPECIFIC` | Bounded, optional private help that never acts for the student |
| N/A | Close Books | `BBB_SPECIFIC` | Readiness gate without hidden-control disclosure |
| N/A | Final Client Meeting | `BBB_SPECIFIC` | Independent financial explanation and bounded follow-ups |
| N/A | Client Readiness Report | `BBB_SPECIFIC` | Immutable presentation of authoritative P-006/P-007 results |

“High fidelity” means recognizable information architecture, terminology, decisions, and consequences. It does not authorize copying QBO colors, icons, spacing, layout, trade dress, screenshots, or proprietary microcopy.

## 3. Application frame and navigation

### 3.1 Persistent frame

Every attempt-owned screen uses the same frame:

- top bar: `BBB Client Practice Lab`, student account menu, and Help entry;
- engagement context: `Suncoast Home Services LLC`, `June 2026`, and `Attempt N`;
- primary navigation: Dashboard, Transactions, Sales, Expenses, Accounting, Reports, Documents, Client Inbox;
- secondary BBB actions: BBB Coach and Close Books;
- route content with a single page title and a short task-oriented description;
- no score, hidden progress meter, scenario counter, or readiness prediction.

The active attempt ID comes from server-authorized session context. A route parameter can identify an attempt for navigation, but every request must still be resolved by authenticated student plus attempt. A foreign, stale, or guessed ID receives the same unavailable state.

Internal attempt IDs are never used as visible labels, headings, breadcrumbs, or error details. The student sees the company, period, and human-readable `Attempt N`. The frame uses distinct visual treatment for the client workspace versus the student's BBB account so the student cannot mistake case data for BBB administrative data.

## 4. Shared interaction rules

### 4.1 Money, dates, and statuses

- Display money as signed US currency with cents; preserve integer cents in all requests.
- Display case dates in `MMM D, YYYY`; do not silently substitute the viewer's current date.
- A debit/credit view uses explicit columns. A bank-feed view uses one signed Amount column.
- Use text plus icons for status; never rely on color alone.
- Do not label an entry correct/incorrect. Show its operational state and natural financial consequence.

### 4.2 Drawers and drill-through

Tables open a route-addressable detail drawer on wide screens and a detail page on narrow screens. The URL must preserve the selected record so refresh and browser history work. A detail can link only to records already authorized in the student projection.

Standard links are:

- bank activity → candidate bookkeeping transaction or create/categorize decision;
- customer → invoice → payment/application → deposit;
- report row → contributing journal entries → source operational record;
- chart-of-account row → register;
- document link → authorized related record;
- Client Inbox request → newly authorized document when the domain unlocks it.

Cross-area navigation carries an origin token containing only an owned route and public filter/selection state. Documents, Client Inbox, Coach, report detail, and register detail show `Return to [work item]`; browser Back restores the same filter, source account, and selected row. The server reauthorizes both the destination and return target, and the token never contains instructor context or becomes authority by itself.

No drill-through endpoint may expose instructor provenance, source-template IDs, hidden scenario mappings, clean-state values, or critical hooks.

### 4.3 Mutation feedback

- Disable submission while a request is pending; use idempotency where the domain supports it.
- Success identifies the student's action, not its correctness: e.g. `Transaction recorded` or `Payment matched`.
- Bounded errors use `Unavailable`, `This action is no longer available`, or the domain's student-safe explanation.
- Never repair, plug, auto-balance, auto-match, or silently choose an account.
- Confirm destructive-looking bookkeeping changes with their visible consequence. Reset/retry is a separate attempt, never an overwrite.

### 4.4 Loading, empty, error, and conflict states

P-009 must provide all of these shared states:

| State | Student experience | Security/integrity rule |
| --- | --- | --- |
| Loading | labelled skeleton or progress text in the existing page structure | no stale data from another attempt |
| No records | neutral explanation plus relevant next navigation | never claims the work area is correct or complete |
| Unauthorized/unknown attempt | `This workspace is unavailable` with safe return navigation | same response for absent and foreign records |
| Unavailable document | `This document is unavailable` | no title, identifier, existence, lock reason, or remaining count |
| Stale action | explain that the record changed and offer refresh/review | do not replay against a different version |
| Failed save | retain the student's entered values where safe and permit retry | do not claim success or partially mutate client state |
| Reconciliation conflict | return to current reconciliation data with bounded review copy | no fingerprint, hidden transaction, or instructor diagnostic |
| Reset failure | keep the current attempt active and unchanged | never leave two ambiguous active workspaces |

### 4.5 Destructive and high-risk actions

Confirmation is required for Exclude/remove, void where supported, account consolidation, reconciliation completion, and reset/retry. The confirmation identifies the visible bookkeeping consequence and whether the action is reversible. It never reveals that an action is scored or tied to a critical hook.

Ordinary reversible actions—opening a record, filtering, clearing/unclearing before reconciliation completion, or saving a non-destructive draft—do not receive unnecessary confirmation. No one-click `Fix Duplicate Accounts`, `Make Adjustment`, `Fix Difference`, or similar repair action is permitted.

### 4.6 Audit without a surveillance experience

The application may show ordinary business history such as who/what was recorded, message chronology, document activity, completed reconciliation, and attempt history. It does not display `this action is being scored`, assessment event feeds, scenario progress, instructor observation state, or constant audit warnings. Assessment remains behind the practice experience.

### 4.7 Help placement

BBB Coach is available from the global frame and contextually from supported communication records/drafts. It may explain an investigation or communication approach but never preselect a banking action, account, match, reconciliation item, or report conclusion. Help history remains attempt-local and visible as help history—not a punishment or score preview.

## 5. Dashboard specification

### 5.1 Purpose

Orient the student to the client, period, current books, and legitimate work surfaces. The Dashboard is not a task list generated from the answer key.

### 5.2 Header

- `Suncoast Home Services LLC`
- `June 2026`
- `Attempt N`
- neutral attempt status such as `In progress`, `Ready for final review`, or `Completed`, only when supplied by an authorized workflow state

### 5.3 Summary cards

Cards contain current student-book values and link to their source screen:

1. Operating Checking — current ledger balance; opens its register.
2. Accounts Receivable — current customer subledger total; opens A/R Aging.
3. June Income — current selected-basis revenue; opens Profit and Loss.
4. June Expenses — current selected-basis expenses; opens Profit and Loss.

Each card identifies its basis or as-of date. Values update only from authoritative domain responses. Dashboard composition must not cache independent totals.

### 5.4 Operational status

Below the financial overview, show only direct public workflow state:

- Client follow-up: unread Michael messages and student-requested document follow-up, without hidden expected requests;
- Checking reconciliation: not started, in progress, balanced, or completed;
- Visa reconciliation: not started, in progress, balanced, or completed;
- Close status: In Progress, Not Ready, Ready for Final Review, or Completed.

`Balanced` describes a zero current difference; `Completed` means the server accepted and preserved reconciliation completion. Neither implies the whole engagement is correct. Status is never inferred from hidden control completion.

### 5.5 Work areas

A `Continue bookkeeping` section contains navigational cards, not inferred tasks:

- Review bank transactions
- Review sales and customer activity
- Review expenses and card activity
- Reconcile accounts
- Review reports
- Check documents
- Open Client Inbox

Permitted badges represent direct, non-evaluative state such as unread client messages or documents currently available. Prohibited badges include `13 problems`, `7 tasks remaining`, `82%`, `almost correct`, or counts derived from hidden scenarios.

### 5.6 Dashboard states

- loading: labelled skeletons retaining page structure;
- normal: values and navigation;
- no active attempt: bounded start/resume state;
- stale/foreign attempt: generic unavailable state;
- completed historical attempt: read-only with report/history entry when authorized.

### 5.7 Dashboard acceptance criteria

- A student can identify client, period, attempt, cash, A/R, income, expenses, and next work surface without explanation.
- Every amount reconciles exactly to the current attempt's authoritative ledger/subledger response.
- No hidden-case progress or scoring signal appears.
- Values do not disclose the clean master or expected ending state.

## 6. Bank Transactions specification

### 6.1 Purpose and fidelity

This is the primary recognizable QBO-style workflow. It presents independent bank activity and asks the student to decide how that activity relates to the books. It must make `Categorize`, `Match`, `Transfer`, `Exclude`, and `Review` recognizable mental choices without copying QBO's visual design.

### 6.2 Page structure

Header:

- title `Bank Transactions`;
- selected source account;
- source period/date range;
- statement/source identity where student-authorized;
- filters: date, amount, description, review state;
- tabs: `For review`, `Recorded`, `Excluded` only if backed by explicit student workflow state.

Primary table:

| Date | Description | Amount | Category or Match | Action |
| --- | --- | ---: | --- | --- |
| Jun 12 | Susan Martinez | $3,850.00 | Review | Review |
| Jun 17 | ABC Trailer & Equipment | $2,400.00 | Review | Review |
| Jun 22 | Home Depot | $642.18 | Materials & Supplies | Review |
| Jun 22 | Home Depot | $642.18 | Materials & Supplies | Review |

Rows are examples of layout, not hardcoded UI truth. P-009 must obtain all displayed records and allowed actions from an attempt-safe adapter. The two legitimate Home Depot rows remain visually ordinary; the UI must not mark them as a duplicate test.

The feed includes authentic ordinary activity as well as records that warrant investigation. Ordinary valid rows use the same typography, actions, and review treatment as assessed records. No suspicious icon, accent color, sorting priority, warning badge, or recommended action may be derived from scenario membership, instructor metadata, clean truth, or hidden scoring weight.

### 6.3 Review workspace

Selecting Review opens a workspace with:

- source activity: date, description, amount, source account;
- current status;
- candidate matches, if returned by an authorized matching query;
- tabs or segmented choices: `Match`, `Categorize`, `Transfer`, `Exclude`;
- links to related authorized customer/payment/deposit, document, register, or Client Inbox context;
- optional note/memo where supported;
- explicit `Record` action and `Cancel`.

The UI must not rank a candidate as “correct,” reveal why a candidate exists, or invent matching. Candidate generation and match eligibility belong in a P-009 application adapter over existing operational records. If the current backend cannot safely provide a choice, the screen shows `No available match` and permits investigation; it does not synthesize one in the browser.

### 6.4 Match

The Match view shows candidate record type, date, counterparty/customer, amount, and lifecycle context. For a customer receipt it can expose the authorized chain:

```text
Invoice → Payment → Undeposited Funds → Bank Deposit
```

The student confirms the match. The server validates attempt ownership, amount and source compatibility, and current state atomically. Matching does not create duplicate income.

### 6.5 Categorize

The Categorize view requires payee/description context and an attempt-owned account selection. Account choices show name and account type. The UI posts the student's explicit decision through a domain application service; it does not generate journal lines client-side. If the student categorizes a receipt as income that was already recorded, resulting duplication must arise naturally in the ledger, reports, A/R/payment chain, and reconciliation—not through a “wrong answer” banner.

### 6.6 Transfer

Transfer requires another attempt-owned balance-sheet account and disallows the same source/destination. The server owns the balanced posting. P-009 must not add transfer behavior until an existing or explicitly in-scope adapter can represent it without bypassing double-entry controls.

### 6.7 Exclude

Exclude requires explicit confirmation and preserves an attempt audit event. Exclusion means “do not add this bank-feed activity”; it must not delete an existing journal entry or source evidence. The confirmation explains that excluded activity remains in history and can leave the books or reconciliation incomplete. Domain assessment evidence must still observe an inappropriate exclusion when an authorized exclusion command marks a critical action; the UI cannot suppress that event. If P-009 lacks a domain command for durable exclusion, the control remains specified but disabled with neutral `Not available in this version` copy—never emulated only in browser state.

### 6.8 Investigate from a row

The workspace offers non-answering routes:

- `View related records`
- `Search documents`
- `Ask Michael` (opens Client Inbox with no prewritten conclusion)
- `Ask BBB Coach` (opens bounded help context)
- `View account register`

The expected ABC workflow is navigation, not a wizard:

```text
Bank Transactions → Client Inbox → request support → Documents
→ Bank Transactions → explicit bookkeeping decision
```

The UI must not automatically unlock a document merely because the workspace was opened. Existing P-003/P-004 authorization rules remain authoritative.

### 6.9 Bank Transactions states and accessibility

- Preserve filters and selected row after navigating to Documents or Client Inbox.
- Keyboard users can move through rows, open Review, choose an action, and submit without drag/drop.
- Duplicate-looking rows have unique accessible labels including date, description, amount, and stable row position—not hidden IDs.
- Empty state says no transactions match the current filters, not that banking is complete.
- Concurrent/stale mutation returns a bounded refresh state.

### 6.10 Bank Transactions acceptance criteria

- A QBO-certified student recognizes the review/match/categorize/transfer/exclude workflow without a tutorial.
- Susan's receipt can be traced through invoice, payment, Undeposited Funds, and deposit before the student chooses an action.
- Categorizing versus matching produces ledger-derived consequences without correctness banners.
- ABC can be investigated through Michael and Documents without hidden guidance.
- Identical Home Depot amounts do not create a visual or textual answer-key hint.
- No client-supplied account, transaction, match, or attempt ID can cross attempt ownership.

## 7. Sales and customer screens

### 7.1 Customers

Columns: customer, open invoices, unapplied payments, net receivable, status. Customer detail shows invoices, payments, applications, and deposit links. Amounts come from `customerBalances` and operational records. The page never labels Jenkins, Reynolds, or another balance as expected/correct.

Susan Martinez, David Reynolds, Robert Jenkins, Palm Breeze, and ordinary customers all use the same customer-detail contract. Their visible invoice/payment/deposit histories—not scenario membership—determine what appears. Reynolds's application can therefore be investigated through normal payment allocation, Jenkins through open receivables, Susan through the complete receipt/deposit chain, and Palm Breeze through its authorized records without any assessment-control label.

### 7.2 Invoices

List columns: invoice date, customer, due date, original amount, applied, open, status. Detail shows line items, revenue accounts, journal entry, payment applications, and documents already authorized. Primary actions are only those supported by the server's operational service.

### 7.3 Receive Payment / Payment History

Show payment date, customer, method/reference, amount, destination account, applied and unapplied amounts, invoices applied, and deposit membership. Creating or applying a payment must use atomic application-level commands and fail closed on cross-customer/cross-attempt or over-application references.

### 7.4 Bank Deposits

Show date, destination bank account, total, included payments, and journal entry. Creating a deposit selects eligible attempt-owned Undeposited Funds payments. It cannot include a payment twice, cross attempts, or accept a client-computed total that disagrees with membership.

## 8. Expense, card, chart, and register screens

### 8.1 Expenses

List columns: date, payee/description, payment account, category, amount, and source/document indicator. Detail shows the authoritative journal entry and authorized evidence links. Editing behavior is limited to existing P-002 commands and cannot mutate template/source truth.

The Home Depot pair, Sherwin-Williams activity, pressure-washer purchase, ABC transaction, and ordinary expenses receive identical row treatment. History shows only actual student/bookkeeping actions. A visible document can aid investigation but cannot display an expected category or correctness state.

### 8.2 Credit Card Transactions

Use the same review vocabulary where applicable, with the card account clearly identified. Card payments and charges remain distinct. Link to the card register and reconciliation. Do not treat an apparent personal charge as resolved or disclose its expected classification.

The Visa detail makes the lifecycle explicit: a card purchase increases the card liability and a payment from Operating Checking reduces that liability. A card payment is not presented as a second operating expense. The $286.43 activity remains an ordinary ambiguous card transaction until P-004/P-003-authorized clarification becomes visible; no badge, document title, category default, metadata, or special styling reveals personal purpose early.

### 8.3 Chart of Accounts

Columns: code, name, type, detail/role when public, current balance, and `View register`. Similar names such as Advertising, Advertising Expense, Marketing, and Marketing & Advertising must remain ordinary rows. Consolidation is an explicit server command with impact confirmation and immutable history; the UI never recommends the clean-master account.

### 8.4 Registers

Header: account name/type and as-of balance. Columns: date, description, source/type, debit, credit, running balance, reconciliation status. Values derive from journal lines. Selecting a row opens the journal entry and its operational source. No stored running total becomes authoritative.

## 9. Reconcile specification

### 9.1 Setup

Inputs preserve the familiar mental model:

- account;
- beginning balance and beginning date;
- ending balance;
- ending date.

Statement values come from the independent authorized statement source, not from the ledger being reconciled. Existing reconciliation history is read-only after completion.

### 9.2 Workspace

Summary remains visible:

- Beginning balance
- Ending balance
- Cleared balance
- Difference

Table columns: cleared checkbox, date, payee/description, payment, deposit. The Difference updates from the server-authoritative reconciliation calculation or an exact shared domain projection, never a separate UI formula used as truth.

No scenario name or “wrong transaction” hint appears. `Finish reconciliation` is enabled only at zero difference with intact historical fingerprints and server approval. Forced adjustment or plug is not offered.

### 9.3 Completion

Completion records the immutable reconciliation and displays a read-only summary. If historical lines later conflict, the domain's historical-integrity failure is surfaced as a bounded unavailable/review state rather than silently repaired.

The student-facing historical state says that previously reconciled activity has changed and directs the student to compare the account register with the statement and reconciliation history. It does not mention fingerprints, integrity hashes, hidden hooks, or which transaction the instructor expects them to inspect. `Balanced` remains a current zero difference; `Completed` remains the accepted immutable completion event.

## 10. Reports specification

### 10.1 Report center

Cards: Profit and Loss, Balance Sheet, Accounts Receivable Aging, General Ledger, Account Registers. Reports show basis and period/as-of controls only where the existing reporting domain supports them.

### 10.2 Profit and Loss

Support cash/accrual basis and period. Rows show account and amount; totals are ledger/subledger derived. Drill-through supplies contributing entries for that account/period.

The basis switch is limited to the existing P-000A operational cash/accrual projections. Copy describes how this report recognizes the attempt's supported invoice/payment activity; it must not claim tax-basis conversion, full GAAP adjustment automation, inventory basis conversion, or a general-purpose QBO reporting engine.

### 10.3 Balance Sheet

Show assets, liabilities, equity, current earnings, total assets, and total liabilities/equity as of the selected supported date. No balancing plug or clean-master variance.

### 10.4 A/R Aging

Show customer, invoice/due date, original amount, applied, open amount, and days past due. Drill through to customer/invoice/payment application.

### 10.5 General Ledger and registers

General Ledger groups journal lines by account and exposes entry date, description, debit, credit, and running balance. It is a projection of journal lines, never a parallel financial data store.

## 11. Documents, Client Inbox, and BBB Coach

### 11.1 Documents

List only `AVAILABLE_AT_START` or `UNLOCKED` documents. Columns/cards show title, type, date, issuer, and authorized related records. Open/download/follow-reference actions preserve the P-003 audit. Locked-document titles, counts, facts, and identifiers remain absent. A student may request support without learning whether a hidden document exists.

### 11.2 Client Inbox

Conversation list and message history preserve exact chronology and sender. Compose accepts the student's words and never pre-populates a solution. Client responses remain deterministic P-004 behavior based only on authorized intent and information horizon. Links to newly available documents appear only after server authorization.

Michael is labelled `Client` and BBB Coach is never present inside the client thread. A short persistent note explains that client recollection can be incomplete and should be evaluated with available records; client messages are not visually certified as accounting truth. Predetermined question buttons may not replace free-form composition as the primary interaction.

### 11.3 BBB Coach

The student can request Hint, Direction, or Walkthrough for a supported sent message or unsent draft. Show the exact referenced text, coaching response, help level, and history. Coaching cannot send, edit, post, match, categorize, reconcile, unlock, score, or close on the student's behalf.

Coach surfaces are labelled `Private — not shared with Michael`. Hint, Direction, and Walkthrough explain increasing assistance without pass/fail language. Walkthrough wording stays in the private panel and is never copied into or auto-sent through Client Inbox. Michael responds first; unsolicited reflection appears only after the P-005-authorized interaction and never interrupts every message.

## 12. Close Books, Final Client Meeting, and Readiness Report

### 12.1 Close Books

Primary action: `I'm Ready to Close the Books`. Supporting copy asks the student to confirm they reviewed books, evidence, and reconciliations without enumerating hidden controls. The server records the P-006 close attempt and returns only `Not ready`, `Blocked`, or `Ready for final review`. Do not show unresolved scenario counts, expected balances, or points.

This is presented as a professional month-end assertion, not `Submit exam`. When not ready, the UI may direct the student to public work categories already visible in their workspace—books, requested evidence, or reconciliation—only when the server's student-safe result authorizes that category. It must not identify a transaction, customer, document, count, or expected correction from instructor knowledge.

### 12.2 Final Client Meeting

Available only after the P-007 gate. Present the immutable financial package and Michael's neutral opening: `Okay. How did we do this month?` The student submits one independent explanation before any help. Follow-ups, exact responses, and post-performance help preserve chronology. Do not display dimension weights, expected topics, model answers, or interim scoring.

### 12.3 Client Readiness Report

Available only after an immutable P-008 report exists. Render the existing student DTO in its defined order: header/result, points, five competencies, strengths, development, independence/help, self-correction, critical summary when applicable, communication, Month-End summary, recommendation, targeted practice, and attempt/report history. Do not reword, rescore, recompute, or enrich it in the client.

The result is a Lab 1 readiness recommendation, not a certificate, badge, credential, license, or guarantee.

The navigation label is `Results`; the destination page title is `Client Readiness Report`. This gated destination is visually separated from day-to-day bookkeeping navigation and reads as the culmination of the engagement.

## 13. Attempt lifecycle

- Start Lab: create a new authorized attempt only when the student has no resumable active attempt; otherwise offer Resume and explicit historical-attempt navigation.
- Meet Suncoast: show the safe engagement overview once at entry and keep it available from Dashboard help/context.
- Active attempts allow supported mutations.
- Completed/reset historical attempts are read-only.
- Retry creates a new attempt/generation with fresh mutable bookkeeping, locked evidence state, conversation/coaching state, assessment, meeting, and report lifecycle.
- Attempt switching is explicit. Attempt 2 never replaces Attempt 1 in history.
- Deep links always retain attempt context and are reauthorized server-side.

Reset/retry requires this consequence to be stated before confirmation: `Your current attempt will be preserved in your history. A new attempt will begin from Suncoast's original practice starting state.` The copy never says the clean master is reset, never exposes an internal attempt ID, and never promises to erase assessment history. If reset fails, the current attempt remains active and unchanged.

## 15. Responsive and accessibility contract

- Meet WCAG 2.2 AA for keyboard access, focus visibility, labels, contrast, error association, and status announcements.
- Desktop is the primary professional bookkeeping experience and prioritizes dense accounting tables, side-by-side source/detail inspection, and persistent reconciliation summaries.
- Small screens use labelled row cards or dedicated detail pages without hiding financial columns. Wide ledger/reconciliation tables may use an explicitly labelled horizontal scroll region with frozen row identity; they must not collapse debit, credit, cleared state, or Difference into an unusable summary.
- P-009 does not spend scope imitating a mobile QBO application. Mobile behavior preserves comprehension and safe actions; desktop proves the full bookkeeping workflow.
- Tables have captions, sortable-header state, and currency values announced with sign/context.
- Forms use programmatic labels and instructions; dialogs have labelled titles/descriptions, contained focus, Escape behavior where safe, and focus restoration. Validation and save errors are associated with the affected control and announced.
- Focus returns predictably after drawer close or mutation.
- Reduced-motion preference is respected.
- No timed tasks, hover-only facts, color-only reconciliation state, or inaccessible canvas reports.
