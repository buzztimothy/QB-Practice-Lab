# P-009 Student Application Shell and Core Workflow

## Boundary

P-009 adds a locally executable, server-rendered student application over the existing P-000–P-008A domain. It does not add accounting policy, case truth, assessment rules, deployment configuration, or an alternate browser-side state store.

`StudentApplication` is the composition boundary. Every request starts with authenticated student context, resolves an attempt through an ownership check, and returns a newly constructed student DTO. A missing attempt and a foreign attempt both fail with `Attempt not found`. Historical and completed attempts are read-only. Reset preserves the prior record and constructs a new P-008A command session from the original P-002 starting state.

The P-009 local HTTP shell uses one fixed local-development identity because production authentication is outside this phase. Client-supplied student identity is never accepted. Deep-linked attempt IDs are reauthorized by `StudentApplication` on every view and mutation.

## Authority and mutation map

All financial mutations execute `executeStudentCommand` against the owned `StudentCommandSession`, with expected revision and idempotency identity. The application never accepts journal lines and never replaces an aggregate from a browser payload.

| UI workflow | Authoritative P-008A command |
| --- | --- |
| Review / verify / flag | `REVIEW`, `VERIFY_UNCHANGED`, `FLAG_UNRESOLVED` |
| Match | `MATCH` |
| Categorize / reclassify | `CATEGORIZE` |
| Transfer | `TRANSFER` |
| Exclude | `EXCLUDE` |
| Payment application | `REAPPLY_PAYMENT` |
| Bounded transaction edit | The applicable `CORRECT_*`, `RESOLVE_*`, or `RESTORE_HISTORICAL_TRANSACTION` command, selected server-side from the owned record |
| Account merge | `CONSOLIDATE_ACCOUNTS` |
| Reconcile selection / finish | `SET_RECONCILIATION_LINE`, `FINISH_RECONCILIATION` |

Stale commands return a bounded refresh message. Idempotent replay returns the already committed state. The UI waits for the authoritative response and announces saving; it does not optimistically alter accounting state.

Evidence, client conversation, and coaching mutations call P-003, P-004, and P-005 pure domain operations. Close, meeting, and Results call P-006, P-007, and P-008 functions. The application stores their immutable outcomes alongside the active command session and never calculates new scores.

## Student DTOs and secrecy

The browser receives only an application projection assembled from `studentCommandView`, the P-003/P-004/P-005 student projections, ledger-derived reports, and the P-007/P-008 student projections. P-002-origin entries use neutral descriptions and sources. Before the personal-card evidence horizon opens, Owner Draws is removed from accounts and report rows as well as forms. Locked documents, unlock rules, scenario/provenance data, clean state, assessment evidence, critical hooks, reconciliation fingerprints, instructor explanations, and report source references are never serialized.

Reports and dashboard balances are recomputed from posted journal lines and operational subledgers. Profit and Loss supports the existing bounded cash/accrual projection. Balance Sheet, A/R aging, registers, and reconciliation results remain server-derived. There are no stored report totals, reconciliation plugs, or client-side accounting formulas.

## Web shell

The server-rendered application implements Meet Suncoast, Dashboard, Bank Transactions, Sales/Customers, Expenses/Visa, Chart of Accounts, registers, Reports and drill-through, Documents, Client Inbox, private BBB Coach, Reconcile, Close Books, Final Meeting, Results, and attempt history/reset. Persistent client, period, attempt, revision, and return context are rendered in the shell.

The shell uses semantic headings, navigation, captions, row headers, labelled forms, live status announcements, confirmation prompts for consequential actions, visible focus, reduced-motion support, and horizontally scrollable labelled accounting tables. Desktop keeps dense accounting relationships; narrower layouts preserve columns through explicit scrolling rather than ambiguous financial cards.

## Reachability and tests

`tests/student-application.test.ts` proves start/resume, ownership denial, serialization secrecy, ordinary bank rendering, P-008A command mapping, stale/idempotent behavior, document/client/coach investigation, semantic accessibility, protected resolution, both reconciliations, close, final meeting, Results, and immutable reset/history. The protected-resolution test begins from `StudentApplication.start` and reaches Results using only application actions, visible documents/messages, and P-008A commands—no clean-state builder, instructor helper, or direct aggregate replacement.

P-010 remains responsible for the separately scripted browser-level end-to-end acceptance phase.
