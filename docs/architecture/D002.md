# D-002 Preview Infrastructure Implementation

## Scope and authority

D-002 implements the D-001 Preview topology without changing its provider or trust decisions: Clerk Pro authenticates, BBB maps an immutable Clerk subject to one internal student, and BBB issues its own durable opaque session. Neon Launch is the persistent PostgreSQL authority and one Render Starter raw-Node service is the browser/API origin. This phase adds no Lab feature and admits no real pilot student.

The authoritative origin is `https://preview.clientpracticelabs.com`, backed by the controlled root domain `clientpracticelabs.com`. Render and Clerk Production must both verify that hostname before authenticated Preview traffic is accepted. `https://app.clientpracticelabs.com` is reserved conceptually for future Production and is not configured by D-002; the root domain is likewise not consumed by Preview.

## Authentication and identity

`ExternalIdentityLink` is the durable ownership mapping. `provider + subject` is unique and the database rejects reassignment of provider, subject, or internal student. Email is normalized contact/invitation data, never the ownership key. `PreviewInvitation` pre-authorizes one email for one internal student; a verified Clerk identity consumes a `SENT` invitation transactionally. A valid but unmapped identity receives the same bounded unavailable result as inactive and unknown identities.

The hosted Clerk flow returns to `/auth/callback`. That same-origin page submits an identity-free POST to `/auth/exchange`. The adapter verifies the Clerk session with the supported backend SDK, configured JWT key, issuer, audience, and exact authorized party, then fetches the backend user to require an unlocked, unbanned account and a verified primary email. Mapping, invitation consumption, student activation, existing-session revocation, and new hashed-session creation are one database transaction.

The BBB cookie remains a 256-bit opaque token with only its SHA-256 digest stored. It is host-only, `HttpOnly`, `Secure`, `SameSite=Strict`, path `/`, server-expiring, replace-on-exchange, and revocable on logout or account lifecycle change. Clerk state never replaces server-side attempt ownership checks.

Signed `/auth/webhooks/clerk` events support `user.updated` and `user.deleted`. Provider event IDs are unique for replay safety. Email updates retain the immutable subject mapping. Delete, ban, or lock deactivates the student/link and revokes all BBB sessions while preserving attempts and bookkeeping history.

## Production configuration

Startup rejects non-production mode, disabled durable runtime, any `LOCAL_AUTH_ENABLED` value except absent/`false`, missing database or Clerk configuration, a non-HTTPS/non-exact origin, authorized-party mismatch, invalid session TTL, and canonical version mismatch. Readiness additionally requires the D-000R canonical record and digest to match. No in-memory or fictional-identity fallback exists in Preview.

Render receives only the pooled least-privilege runtime URL. `DIRECT_DATABASE_URL` exists only in the protected `bbb-preview-deploy` GitHub environment. The deployment workflow accepts only the exact current `main` SHA, serializes through GitHub concurrency and a PostgreSQL advisory transaction lock, migrates, bootstraps twice for idempotency, triggers Render, and waits for `/health/ready`. PR code has neither Preview secrets nor an automatic Preview deployment path. Migrations follow expand/migrate/contract compatibility.

## Provisioning and operations

Compile first, then provision only fictional Preview testers with:

```text
CLERK_SECRET_KEY=<secret> DATABASE_URL=<deploy-url> pnpm preview:invite -- --origin <exact-preview-origin> --student-id <opaque-id> --display-name <fictional-name> --email <controlled-address>
```

The command creates the internal student/invitation before requesting a Clerk invitation, records only the provider invitation identifier, and never logs secrets or a provider subject. The legitimate Clerk activation and verified exchange establish the subject mapping. Deactivation is transactional through `PreviewProvisioningService`; provider-side revocation/ban remains an operator action in Clerk.

Destructive database tests require `DATABASE_LIFECYCLE_MARKER=disposable-test` and a database name containing `test`, `validation`, or `disposable`; they categorically reject `bbb_practice_preview`. Preview migration/bootstrap requires both the exact database name and `PREVIEW_DATABASE_CONFIRMATION=bbb_practice_preview`.

## External checkpoint record

Resource identifiers, plans, regions, recovery window, canonical digest, origin, and bounded smoke results belong in the D-002 completion record after each external checkpoint. Secrets, connection strings, tokens, cookies, manifests, instructor data, and student payloads must never appear in that record or logs. If actual provider behavior, tier, price, invite restriction, role separation, raw-Node hosting, or recovery capability differs materially from D-001, provisioning stops for review.
