# D-000 Durable Runtime and Persistence Foundation

## Decision

D-000 retains the small `node:http` server and the existing framework-independent domain. A framework migration would not improve the durability boundary and would increase behavioral risk. The web server remains the public request adapter; `StudentApplication` remains the student-safe composition boundary; `StudentAttemptRepository` is the durable authority boundary. `PrismaStudentAttemptRepository` makes requests stateless over PostgreSQL. A hosting platform only needs a replaceable Node 22 process, PostgreSQL connectivity, environment variables, and HTTP health routing.

`DURABLE_RUNTIME_ENABLED=true` selects the PostgreSQL adapters. `NODE_ENV=production` without that setting terminates at startup. There is no production-shaped in-memory fallback. The in-memory repository and authenticator remain explicit test/local adapters only. `LOCAL_AUTH_ENABLED=true` is still required for fictional Student A/B login and remains impossible in production.

## Persistence inventory

| Existing state | Classification | D-000 authority |
|---|---|---|
| `StudentApplication.attempts` and `histories` | Authoritative | `runtime_attempts`, owned by `runtime_students`; generation and status are relational |
| P-002 accounting and operational records | Authoritative relational state | P-000/P-000A `student_attempts`, attempt accounts/customers, journal entries/lines, invoices, payments, applications, deposits, and reconciliations |
| P-002 transformation metadata | Non-financial workflow context | bounded `p002_metadata_state`; it contains no journal, subledger, reconciliation, or report-total authority |
| P-002 action and correction history | Authoritative append-only chronology | relational `attempt_actions` plus immutable `runtime_audit_events` |
| P-003 document state, unlocks, evidence audit | Authoritative aggregate | `evidence_state` |
| P-004 conversations, messages, disclosures | Authoritative aggregate | `interaction_state` |
| P-005 coaching and help chronology | Authoritative aggregate | `coaching_state` |
| P-006 assessment and close evidence | Authoritative and historical | current `assessment_state` plus immutable `runtime_snapshots` |
| P-007 meeting and financial-context evidence | Authoritative and historical | current `meeting_state` plus immutable `runtime_snapshots` |
| P-008 report history | Authoritative and historical | current `report_state` plus immutable `runtime_snapshots` |
| P-008A receipts and revision | Authoritative concurrency data | relational `runtime_idempotency` and `runtime_attempts.revision` |
| P-009A session `Map` | Authoritative security state | `student_sessions`, looked up by SHA-256 token hash |
| View-model account-name and report maps | Derived/recomputable | Remain request-local |
| Canonical TypeScript definitions | Versioned source material | Verified by `canonical_lab_bootstrap`; never mutated by student writes |

The aggregate columns are deliberately separated by bounded domain responsibility; the application is not stored as one opaque process image. Accounting is rehydrated exclusively from the existing relational ledger and operational subledgers. Balanced journal lines remain financial truth, and reports are recomputed from them. `runtime_historical_reconciliation_lines` preserves accepted fingerprints for lines deliberately removed or changed by the P-002 starting defects; those immutable rows are historical evidence, not current posted activity. PostgreSQL ownership, role, balance, application, deposit, and reconciliation checks therefore protect the same rows used by the running application. JSON columns hold only bounded evidence, interaction, coaching, assessment, meeting, report, and non-financial transformation context.

## Ownership, transactions, and concurrency

Every read is `attempt id + authenticated student id + canonical Lab version`. Foreign and nonexistent attempts therefore share the same not-found path. Attempt creation requires a relational student and unique `(student, Lab version, generation)`. Reset changes the old attempt and inserts the next generation in one database transaction; prior attempts remain available and read-only.

Every save uses compare-and-swap on `persistence_version`. Domain bookkeeping also validates the accepted P-008A `expectedRevision`. Idempotency receipts are inserted in the same transaction and uniquely constrained by `(attempt, idempotency key)`. A retry on another process rehydrates the receipt and cannot repeat the command. Compound evidence, interaction, coaching, close, meeting, and report transitions are calculated before a single transactional repository save; a failed transaction commits nothing.

`runtime_snapshots` append assessment, meeting, and report states by content hash and sequence. PostgreSQL triggers reject snapshot and audit-event update or deletion. Completed reconciliation records, selected-line fingerprints, and orphaned historical-line evidence are likewise immutable. Corrected mistakes remain in the persisted P-002 audit chronology and later activity does not rewrite historical snapshots.

## Durable sessions and identity boundary

The browser receives a random 256-bit opaque token in the existing `HttpOnly`, `SameSite=Strict`, path-scoped cookie; HTTPS/production adds `Secure`. PostgreSQL stores only SHA-256 of the token with the provider-neutral subject, internal student ID, display name, expiry, and revocation time. Authentication, expiry, logout, and replacement are database-authoritative across instances. Exact-Origin checks remain ahead of every cookie-authenticated mutation.

`external_identity_links` reserves the provider-neutral mapping from `(provider, subject)` to one internal student. D-000 does not choose or implement a provider. A future adapter must validate an external session server-side, resolve an active link, and return the existing `AuthenticatedStudentPrincipal`; browser fields never select identity.

## Canonical bootstrap

`scripts/bootstrap-canonical.ts` installs and verifies `SUNCOAST-L1-2026.08-D000R.1`. Its canonical manifest is the stable serialization of the actual Suncoast command session: P-001/P-001A master data, P-002 controlled state, P-003 evidence, P-004 Michael behavior, P-005 coaching, P-006 assessment inputs, and P-008 report definitions. Bootstrap also installs the canonical template accounts, customers, and document content into their relational source tables and records a second digest of those database rows. Readiness recomputes both digests. Re-running identical content is a no-op; source or database tampering makes readiness false and bootstrap fail closed. Immutable template/bootstrap triggers protect normal operation, and bootstrap never queries or updates student attempts.

Fresh environment order is: committed Prisma migrations, compiled bootstrap, bootstrap verification, readiness, application start. `prisma db push` and test fixtures are not bootstrap mechanisms. Pre-D-000 migrations remain intact; already durable P-000/P-000A data is preserved. Process-local P-002–P-010 state from an old process cannot be migrated because it never existed in PostgreSQL.

## Health and failure behavior

- `GET /health/live` proves only that the process can answer HTTP.
- `GET /health/ready` returns 200 only when PostgreSQL is reachable and both the source manifest and installed canonical database content match the exact versioned digests; otherwise it returns bounded 503 JSON.
- Normal routes return 503 before authentication or application behavior when readiness fails.
- Production startup fails when durable runtime is not explicitly enabled.
- PostgreSQL errors never select local auth, mock students, in-memory attempts, or fake success.

Operational logs must contain bounded startup/migration/bootstrap/authentication/application failure categories only. Raw tokens, cookies, hidden facts, instructor state, and protected DTOs are prohibited. Persistent domain audit and assessment evidence—not runtime logs—remain authoritative.

## Deployment compatibility contract for D-001

Required runtime configuration is `DATABASE_URL`, `DURABLE_RUNTIME_ENABLED=true`, `NODE_ENV=production`, and an exact HTTPS `APP_ORIGIN`; the final provider will add its own server-only variables. Build commands remain `pnpm install --frozen-lockfile`, `pnpm db:generate`, and `pnpm build`. Controlled release order is `pnpm db:migrate`, `pnpm db:bootstrap`, bootstrap/readiness verification, then `pnpm start:web`. The platform must route to a stateless Node process, preserve cookies, provide PostgreSQL network access, and check `/health/ready` before traffic.

The current web server is a credible single-service topology: browser and server application handlers remain same-origin, eliminating new CORS/cookie complexity. `apps/api/server.ts` remains a non-authoritative health stub and must not be deployed as a second business-logic service. D-001 may select a host that runs the Node server directly or adapt the thin HTTP entrypoint to a function signature; it must not duplicate domain logic.

## Security and performance invariants

Student-safe DTO construction remains explicit in `StudentApplication`; Prisma rows are never serialized. Instructor material stays inside server-side aggregates. Exact-Origin enforcement, foreign/nonexistent equivalence, local-auth production disablement, reset isolation, immutable canonical records, journal/report derivation, and P-000/P-000A constraints remain unchanged.

Indexes cover owned attempt/status/generation lookup, idempotency chronology, snapshot chronology, student session expiry/revocation, and provider linkage. Each request loads one owned attempt and its receipts; it does not scan other students or the entire database. No cache is required for correctness.

## Validation model

Disposable PostgreSQL is the authoritative integration environment. D-000 tests create independent Prisma clients to prove restart/instance replacement, cross-instance idempotency and stale-write rejection, cross-student denial, reset history, hashed session resumption, and cross-instance revocation. Tests verify that runtime attempts have no `accounting_state`, that the live application populates the relational ledger/subledgers, and that completed reconciliation history is immutable. Bootstrap is rerun to prove idempotency and attempt preservation; controlled canonical-row tampering makes readiness false and rerun conflict. The accepted P-009 Start-to-Results test remains the behavioral oracle and the complete P-000–P-010R suite must remain green with database enforcement enabled.

No Neon project, Vercel project, domain, production secret, production authentication provider, QuickBooks integration, or Booked integration is part of D-000.
