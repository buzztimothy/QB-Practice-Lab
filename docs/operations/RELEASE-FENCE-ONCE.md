# One-time protected release-fence installation

This temporary workflow installs only `202610220001_preview_release_fence` through Prisma's migration ledger. It cannot recover invitations, bootstrap canonical data or trigger Render. No new secrets, grants or runtime configuration are required.

## Approval and rollout order

1. Owner freezes all deployment/recovery activity, drains queued and running GitHub jobs, and verifies Render Events and external operator shells have no operation underway. Do not cancel an in-flight mutation merely to create an idle state. Keep the freeze until installation is verified, including after any failure.
2. Review and merge PR #29 normally. Review this dependent installer PR, retarget it to main after #29 merges, and merge normally after checks. Verify the resulting exact main SHA includes both corrected operator entrypoints. Never rerun an old workflow or use a pre-merge operator checkout.
3. Verify Settings → Environments → `bbb-preview-deploy`: required owner reviewer, main-only deployment branch restriction and no protection bypass. Existing `DIRECT_DATABASE_URL` must identify the direct Preview deploy role; existing `PREVIEW_DATABASE_HOST` must match the approved host. Do not display or change credentials. The YAML environment reference alone does not guarantee reviewer protection.
4. Record fresh health, deployed SHA, Student A INVITED/SENT with original invitation and zero mappings/sessions/attempts, Student B absent, empty recovery journal and canonical/accounting fingerprints. Stop on drift. Confirm no external deploy hook or operator can start during the freeze.
5. Obtain explicit owner authorization for this one live migration. Actions → One-time Preview release fence installation → Run workflow → main. Supply the full current main SHA and `ALL_OPERATORS_IDLE_FREEZE_UNTIL_VERIFIED`. The owner must separately approve the environment deployment. Do not approve other jobs during this window.
6. The installer reconfirms current main; rejects all other non-completed GitHub runs; validates direct host/database/role/TLS and role restrictions; takes the existing advisory lock on a pinned connection; checks other advisory locks/visible active sessions, empty recovery journal, exact eligibility and complete migration checksums. Any missing session visibility fails closed. Exactly five valid applied migrations and the sole pending fence migration are required. It calls only `pnpm exec prisma migrate deploy`, once, with bounded output. It verifies the completed ledger/checksum, one fresh unheld singleton, runtime SELECT without write/CREATE privileges, and a fingerprint covering every existing application row including all invitation columns and journal rows.
7. Owner reviews successful bounded job output and rechecks health, deployed SHA and baseline fingerprints. Application deployment is unnecessary: this additive metadata installation leaves the running service in place. Only after verification may corrected operators be enabled, always at current approved main and with separate operation authorization.
8. Retire this workflow and its two installer helpers/tests through a separate reviewed removal PR immediately after verified installation; retain this runbook and run URL as audit evidence. Do not remove the migration, shared coordination helper or Prisma ledger. Until removal, an already applied fence is rejected. Never rerun a failed or successful installation.

## Failure and limits

No automatic retry, rollback, ledger edits or fence reset exists. Preserve the operator freeze and inspect the ledger, table and process state after any failure, cancellation or timeout. A migration can have completed even if postchecks failed. Further action requires diagnosis and separate authorization.

GitHub concurrency serializes these three workflows, but cannot detect Render or arbitrary external shells. Their absence is an explicit owner attestation, not an automated guarantee. Read-only GitHub API inventory and database locks add checks; neither substitutes for that freeze. The bootstrap advisory lock is not durable before the migration exists. Connection/process loss therefore must not release the owner freeze. Both corrected operators fail closed before installation; old operators must remain prohibited throughout and afterward.

Credentialed steps emit only fixed stages and booleans. Child output, connection strings, raw rows and tokens are never logged. A mismatch in privileges is reported, never repaired by this installer. No additional permanent workflow or environment is introduced.
